# 第02篇实验与配图设计

[第 02 篇正文](../../docs/drafts/hardware-dataflow.md) 里有两个可以动手检验的问题。做向量加法时，输入长度翻一倍，加法次数和读写量都翻一倍，运行时间也会翻一倍吗？做矩阵乘法时，同样两个矩阵，分成大块计算可以少读几遍输入，算完会快多少？

本篇共七项实验，编号与直接入口见[实验索引](../README.md#实验索引)。手算值与实测数据的对应关系见[真机报告](reports/npu-report.md)。[实验代码与分项运行说明](README.md)已执行，设备时间已归档；HBM 计数字段仍需解释。

# Add：验证容量、流量与并行度

先拿 16384 对 FP32 数做加法。每算一个输出，要读两个数、写一个数，共 12 字节。算完整个向量，程序一共要读写 192 KiB。每个任务一次只处理 2048 对数，两个输入缓冲区和一个输出缓冲区各占 8 KiB。即使向量再长，任务也可以重复使用这 24 KiB 空间。

## Lab02-A1

**把向量加长，时间怎样变？** 每次仍处理 2048 对数，保持任务数相同，只增加向量长度。先逐个检查加法结果，再记录设备算完一遍用了多少秒。重点比较长度翻倍的两次运行。如果短向量长度翻倍而耗时几乎没变，启动一次 Kernel 所需的固定时间可能占了较大比重。如果长向量的耗时也接近翻倍，说明此时平均每秒处理的元素数相近。把每秒处理的元素数乘以 12，就得到按程序读写量折算的带宽。

## Lab02-A2

**同一份输入，多派几个任务会快吗？** 固定向量长度和每块大小，分别让 1、2、4、8 个任务处理同一份数据，再测试设备上选定的任务数。任务越少，每个任务就要多做几轮。如果多派任务能明显缩短耗时，说明之前还有并行处理的余地。如果再加任务也没有改善，接下来要查的是数据能以多快的速度送到计算单元。

## Lab02-A3

**数据真的都从显存读来吗？** 先反复计算同一组数组，再轮换几组互不重叠的数组。反复读同一个地址时，数据可能还在缓存里。两次运行中，代码都要求每个输出读写 12 字节，高带宽内存（HBM）实际传输的字节数却可能不同。用设备的性能分析工具分别记录 HBM 读、写字节数，再和同一设备上独立测得的连续读写带宽比较。这个对照也要保持两读一写的比例。如果轮换大数组后，HBM 带宽接近对照值，增加任务数也不再提速，才有依据说这组 Add 可能受显存带宽限制。设备若读不到这些计数，就报告耗时和按 12 字节折算的带宽，HBM 实际流量留空。

# Matmul：验证理想复用与分块重读

考虑两个边长为 128 的方阵。两个输入用 FP16，输出用 FP32。如果两个输入各读一遍，输出写一遍，合计 128 KiB。现在把输出切成 16 个 $32\times32$ 的小块，让每一块单独取数。横向算四块，同一片左矩阵就要取四遍。纵向算四块，同一片右矩阵也要取四遍。两个输入各占 32 KiB，输出占 64 KiB，合计请求 $4\times32+4\times32+64=320$ KiB。这个差额是下面几组测试要追踪的量。

## Lab02-M0

**先算对一个小矩阵。** 先用边长 64 的方阵核对输入、累加和输出精度，再用边长 128 的方阵沿求和方向分几段算。用单位阵乘一个已知矩阵，逐项检查输出是否等于原矩阵。再用带正负数的稠密矩阵，检查前一段的部分和是否正确加到了后一段。若接口只能输出 FP16，记录 M0 的限制，暂停当前口径的后续实验。

## Lab02-M1

**每块大小固定，把矩阵放大。** 从边长 64 逐步测到 1024，每个输出块先取 $64\times64$ 。每个尺寸记下三样东西：算出多少个输出块、程序为这些块读取了多少输入、算完整个矩阵花了多久。小矩阵可能只够分一个任务，大矩阵可以同时算许多块。因此，随矩阵变大，每秒完成的乘加次数即使提高了，也要看有多少任务参与了计算。

## Lab02-M2

**矩阵大小固定，把每块做大。** 这是直接检验输入复用的一组。用同一对边长 512 的矩阵，沿求和方向每次取 32 个元素，只改输出块的边长。按每个输出块独立取数、部分和留在片上的算法，预期如下。

| 输出块 | 要算多少块 | 程序请求的读写总量（手算） | 每字节对应的运算量 |
| --- | ---: | ---: | ---: |
| $32\times32$ | 256 | 17 MiB | 约 15.06 FLOP/B |
| $64\times64$ | 64 | 9 MiB | 约 28.44 FLOP/B |

先逐块数程序请求读写的元素，再到设备上测时间。**17 MiB 降到 9 MiB 就一定更快吗？** 大块减少了重复读，也把可同时安排的输出块从 256 个减到了 64 个。如果大块反而慢，就检查有多少核分到了工作、设备实际少读了多少字节，以及布局转换用了多少时间。如果接口会自行调整分块，就按它实际采用的方式重新计数。

## Lab02-M3

**离设备的计算上限还有多远？** 用乘加次数折算出真机每秒完成的浮点运算数，再找同设备、同精度的稠密矩阵乘法作对照。厂商给出的理论上限和库函数实际跑出的速度分别列出。画 HBM Roofline 时，横轴用运算数除以 HBM 实际读写字节数，纵轴用运算数除以设备耗时。有了这张图，再结合 Lab02-M1 的任务数和 Lab02-M2 的重读量，才能讨论当前尺寸下限制性能的原因。若缺少 HBM 计数，只画规模、分块与耗时的关系。

# 实施时用哪些参数

- **Add。** 输入和输出都是独立的连续 FP32 数组，每个任务反复使用同一组三块缓冲。Lab02-A1 的长度取 $L\in\{2^{11},2^{12},2^{14},2^{16},2^{18},2^{20},2^{22},2^{24}\}$ ，任务数按设备可用的向量核选定。记录实际拿到数据的任务数和各自处理了几块。Lab02-A2 固定 $L=2^{22}$ ，跳过重复或设备不支持的任务配置。Lab02-A3 尽量让轮换数组的总大小超过已知缓存容量，并记录实际大小。
- **Matmul。** Lab02-M1 的方阵边长取 64、128、256、512、1024。输入为 FP16，累加和输出为 FP32，每次覆盖输出，沿求和方向每段取 32 个元素。Lab02-M2 固定核配置、输入地址和计时范围。边长 128 的输出块只在容量和布局都允许时追加。如果需要单独转换矩阵布局，同时记录“只算矩阵乘法”和“转换加矩阵乘法”的耗时。
- **设备。** 留下实际 SoC、可用矩阵核与向量核数量、驱动和固件可见信息、CANN／ops／编译器版本、编译目标与选项、源码版本和本地修改。逐项核对 UB、L1、L0 的可用空间、布局、对齐和框架预留，再选块大小。记录计时工具、设备是否共享以及可见的频率、温度变化。

## 用手算值检查程序

实现后先用小尺寸逐块枚举地址，把读了几个元素、写了几个元素分别加起来，再乘以各自的元素字节数。和下表逐项核对，可以查出漏算的输入重读，也能发现把每任务缓冲大小乘错了任务数的问题。表中 $F$ 表示浮点运算次数， $Q$ 表示程序读写的字节数， $I=F/Q$ 表示每字节对应的运算量。

| 模型用例 | 预期计数，全部为手算值 |
| --- | --- |
| Add， $L=16384$ 、 $T=2048$ 、FP32 | $F=16384\,\mathrm{FLOP}$ ；读 $131072\,\mathrm{B}$ ，写 $65536\,\mathrm{B}$ ，合计 $196608\,\mathrm{B}$ ；三块 UB 有效负载 $24576\,\mathrm{B}$ ／任务 |
| Add， $L=1048576$ 、 $T=2048$ 、循环处理 | $F=1048576\,\mathrm{FLOP}$ ； $Q=12582912\,\mathrm{B}$ ；三块 UB 有效负载仍为 $24576\,\mathrm{B}$ ／任务 |
| Matmul， $n=64$ ，理想输入各读一次 | $F=524288\,\mathrm{FLOP}$ ； $Q_{\min}=32768\,\mathrm{B}$ ； $I=16\,\mathrm{FLOP/B}$ |
| Matmul， $n=128$ ，理想输入各读一次 | $F=4194304\,\mathrm{FLOP}$ ； $Q_{\min}=131072\,\mathrm{B}$ ； $I=32\,\mathrm{FLOP/B}$ |
| Matmul， $n=128$ 、 $b=32$ ，独立输出块 | $Q_{\mathrm{tile}}=327680\,\mathrm{B}$ ； $I=12.8\,\mathrm{FLOP/B}$ ；16 个逻辑输出块 |
| Matmul， $B_M=B_N=64$ 、 $B_K=32$ ，单缓冲有效负载 | L1 输入共 $8192\,\mathrm{B}$ ；L0A／L0B 各 $4096\,\mathrm{B}$ ；L0C 部分和 $16384\,\mathrm{B}$ ；布局填充与预留另计 |

## 怎样检查结果算对了

Add 使用同一组 FP32 输入在主机上逐个相加。用零、正负整数、带索引标记的数据和固定种子的随机数检查结果。输出先填入标记值，算完查找漏写和错位。另测一次块数不能均分给任务的情况，核对每个位置由哪个任务写入。长度为零时由主机直接返回或拒绝请求。尾块需要的安全搬运方式核对后再测。保存逐元素误差和逐位比较结果，若有差异，先查输入转换与舍入方式。

Matmul 先把输入转成和设备相同的 FP16，再在主机上用 FP64 算出参考结果。除零矩阵、单位阵和小整数外，用固定种子生成 $[-0.5,0.5]$ 内的随机数，另选一组正负乘积相互抵消的输入。记录最大绝对误差、最大相对误差及整块矩阵的相对 Frobenius 误差，并注明计算相对误差时采用的分母下限。

对每个输出元素， $c$ 是设备结果， $c_{\mathrm{ref}}$ 是同一位置的主机参考值。随机用例暂定要求 $\lvert c-c_{\mathrm{ref}}\rvert\le10^{-3}+10^{-3}\lvert c_{\mathrm{ref}}\rvert$ 。左边是两者相差的绝对值，右边是固定误差 0.001 加上参考值绝对值的 0.1%。例如参考值为 10 时，允许误差为 0.011，设备算出 10.008 就通过。任一元素超出阈值，记录它的位置和两个值。

排查累加误差时， $i,j$ 表示输出的行、列， $K$ 是参与点积的数对个数， $k$ 是数对的下标。 $\sum_k\lvert a_{ik}b_{kj}\rvert$ 把对应行、列的元素逐对相乘，取绝对值后求和。普通 FP32 就近舍入模型中， $u=2^{-24}$ 是单位舍入误差。当 $Ku<1$ 时，将上述总和乘以累加误差系数 $\gamma_K=Ku/(1-Ku)$ ，可估计舍入带来的绝对误差范围。最终通过阈值在核对设备的累加方式后确定。

## 怎样计时和记录

1. 可以先用 CPU 或 SIM 查找索引和计算错误，分别记录执行模式。画性能图使用通过正确性检查的 NPU 结果。
2. 计时前准备好数组、分配设备内存并传好输入。等同一条 Stream 上已有的工作完成，再用设备计时工具测 Kernel。输出回传、打印和主机参考计算都放在计时区间外。若只能在主机上等待完成并计时，结果标为“主机等待时间”。
3. 每个配置先预热 20 次，再测 5 组，每组至少 50 次。若只能测整组，就用整组时间除以次数，保留每组均值。如果单次太短，就增加次数，让整组时长至少达到计时分辨率的 100 倍。分别标明数据来自单次还是整组，报告中位数、四分位范围、最小值和最大值。
4. 用固定种子打乱配置的运行顺序，每组前后检查输出。另跑一次相同配置收集性能计数器，并注明工具测的是哪一级存储的读写。保留原始样本、种子、地址轮换方式、实际分块、任务数、失败和超时记录。两种分块的差异若落在重复测量的波动范围内，就如实报告这个范围。
5. 在实验报告里把手算字节数、实际计数和耗时并排放。凡是设备查不到的指标写“不可观测”。报告填写实际实验日期，再把能由数据支持的结论回填正文。
