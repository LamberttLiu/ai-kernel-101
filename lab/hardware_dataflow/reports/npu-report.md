# 从首次失败到正确运行

1. 首次 M0 请求 K 基础块 32，接口返回 64，被严格分块检查拒绝。改为记录实际基础块，要求其能够整除 K，同时保留输出块 32／64 的约束。[首次结果](../results/2026-11-18/M0-first.jsonl)
2. 随后首次设备调用持续等待。安装版本的官方纯 Cube 高阶 Matmul 样例要求 `ASCENDC_CUBE_ONLY`，补齐该定义后完成执行。卡住的本次测试进程已终止。[等待时的记录](../results/2026-11-18/M0-adjusted.jsonl)
3. 继续检查时部分输出仍为 NaN 标记。输入准备后增加设备同步，重新检查通过。正式测量另设置 `TASK_QUEUE_ENABLE=0`，让框架事件与直接 ACL 内核调用按主机提交顺序进入 Stream。[修复前](../results/2026-11-18/M0-cube.jsonl) · [同步后的检查](../results/2026-11-18/M0-sync.jsonl)
4. M3 原用的 `torch.mm(out_dtype=...)` 在当前框架版本报 `TypeError: mm() got an unexpected keyword argument 'out_dtype'`。改用安装版本的 ACLNN 接口，并通过输出 2049 的精度探针后再测量。[成功的库对照](../results/2026-11-18/M3-aclnn.jsonl)

纯 Cube 定义依据本机 cann-samples 中的 `Samples/0_Introduction/01_simd_cpp_api/02_matrix/matmul_advanced_api/matmul_advanced_api.asc`，接口声明依据本机 CANN 头文件。代码入口见[实验源码说明](../README.md)。

# 计时口径

正式测量预热至少 20 次，随后测 5 组，每组 50 次；下表使用五组均值的中位数。输入上传、输出回传与主机参考计算在计时区间外。每组前后检查结果。事件之间仍可能有主机提交间隙，因此单独用 msprof 采集 A3、M2、M3 的内核时间作复核。

每个 Matmul 配置的第一次检查与预热、M0 的检查均从 profiler 统计中剔除。表中 profiler 中位数来自独立采集中的 250 次正式调用，采集本身可能影响时间。分组样本保留在各 JSONL 的 `group` 行，四分位数保留在 `timing` 行。

# Lab02-M0

32、64 两种输出块均在 64、128 阶方阵上通过五类输入检查。零、单位阵、输出 2049 的探针与消去输入要求精确相等；随机输入按设计中的绝对加相对误差判据检查。

实际基础块会随尺寸变化。64 阶时 K 基础块为 64，128 阶时为 128，所以这两种尺寸尚未覆盖多 K 段累加。后续 M1 的 512、1024 阶配置采用 K 基础块 256，补充了多段累加下的随机正确性检查。FP32 输出探针能排查输出降精度，完整累加机制仍需结合接口实现核对。[M0 全部检查](../results/2026-11-18/M0.jsonl)

# 性能计数的归档与待分析项

三次 profiler 的逐算子时间及 Memory 字段已保存在[CSV 目录](../results/2026-11-18/profiler-csv)，分组复核结果见[内核时间摘要](../results/2026-11-18/profiler-summary.json)。A3、M3 另启用了 HBM 系统采样，导出的是整段运行的平均 MB/s。采样包含初始化、回传和主机校验间隔，无法直接当成某次内核的 HBM 字节数。

Memory 导出中的 main_mem、L2 带宽字段需要进一步核对本架构上的事件定义、汇总方式和时间分母。JSONL 的 `hbm_bytes` 因此仍为空。实际 HBM Roofline 暂待这些字段解释及同精度设备峰值确认。
