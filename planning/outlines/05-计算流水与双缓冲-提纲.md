# 第 05 篇提纲：Double Buffer 一定更快吗？用实验拆解计算流水

> 本篇按[系列计划](../series-plan.md)展开，承接[第04篇](../../docs/drafts/vector-add-tail.md)的核内分块设计。当前只有提纲，不代表对应实现、真机验证或正文已经完成。

核心问题：同一个 Add 分成多批之后，多准备一份缓冲，为什么有时能缩短耗时，有时却没有收益？

中心论点：缓冲份数提供重叠条件，真正的收益取决于数据依赖、执行资源、可用容量和任务规模，必须通过受控实验检验。

读者前置：知道 GM→UB→Vector→GM 的数据流，能区分 Block 与 Tile，以及 TQue 深度与 InitBuffer 缓冲块数。第04篇的多轮实现尚未完成，是本篇代码对照的前置缺项。

# 一、数据已经分块，为什么阶段仍然排着队？

从单缓冲每轮“搬入→计算→搬出→复用”切入，标出缓冲占用：输入未消费完不能覆盖，输出未搬完不能改写。同一批数据的依赖不能因为多申请一块空间就消失。

把问题转到不同批次：当第 j 批正在计算，第 j+1 批能否搬入另一份输入缓冲？第 j-1 批的输出能否同时搬出？引出流水，而不是先列 Double Buffer API。

配图位置：单缓冲时间线与缓冲生命周期图，标记为“理论示意”；真机时间线另留位置。

衔接：看到空隙之后，先确认我们准备测量的是哪段时间。

# 二、先把“快了多少”的计时边界画出来

分别定义 Kernel 任务耗时、设备事件覆盖区间、Host 发起并等待的耗时、Host↔Device 搬运和完整调用耗时。若实现由多个任务组成，事件区间可能包含任务间间隙，不能直接称为纯 Kernel 执行时间。

计时方法与输出位置：**待实现。** 初始化、分配、输入生成、结果校验是否计入必须固定；主测是否开启 profiler 也必须声明。不同模式的数据分开，CPU/SIM 耗时不作为 NPU 性能。

固定 FP32 Add 输入各读一次、输出写一次时，逻辑有效带宽定义为 12L / Kernel 时间，其中 L 是元素数。说明它不是 profiler 测得的物理带宽，也不是硬件总线峰值。

衔接：有了相同计时区间，才能检验下面的重叠模型。

# 三、双缓冲改变的是不同批次之间的安排

设每批搬入两个输入、计算、搬出输出的时间分别为 a、c、w，共有 J 批。在忽略启动等固定开销的串行模型中：

$$T_{\mathrm{serial}}=J(a+c+w).$$

若三阶段使用可并行的资源，批次耗时相同、依赖与缓冲足以支持持续供给，理想三阶段流水模型为：

$$T_{\mathrm{ideal}}=a+c+w+(J-1)\max(a,c,w).$$

首项是建立流水，最后一批也需要排空；J=1 时没有跨批次重叠收益。公式是简化模型，不证明两个缓冲必然达到这个时间，更不是双缓冲通用加速倍数。读写共享带宽、内部同步及不等长尾块都可能破坏假设。

图中区分同一批的依赖箭头和不同批的可重叠部分，画出各缓冲何时可用。不能把“存在两份内存”画成“已经并行”。

衔接：代码需要表达这些依赖，而不是仅把队列参数改成 2。
