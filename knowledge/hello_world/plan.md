
以三个问题为入口：
1. 以 hello world 为范例，在 NPU 环境中，这个程序又是如何编译->构建成一个二进制的？类比 C 语言程序通过 gcc 编译器在 CPU 上运行的几步，这个代码程序发生了什么？
2. 在一个无 NPU 的 WSL 环境中，一个程序又是如何运行起来的。CPU 模式和 SIM 模式的区别是什么？
3. 类比 CUDA，Ascend C 是否也有胖树 fat-tree 这种概念。 CUDA 支持面向 PTX 级别优化（例如 DeepSeek 团队曾做过的性能优化），Ascend C 是否也有类似的层级，支持面向该层级的优化吗？

# 主题一

**从 C/C++ 编译模型进入 NPU 异构编译**。

细分成四个问题：
1. **源码如何分流？** 编译器怎样识别 Host 代码、Kernel 入口和 `<<<>>>` 启动语法？
2. **各自编译成什么？** Host 面向 x86-64/AArch64，Device 面向指定的 `dav-2201` 架构，两者是什么关系？
3. **二进制怎样组织？** 目标文件、Fatbin、可执行程序之间的区别是什么？
4. **谁真正加载 Kernel？** 编译完成不等于执行。Runtime 如何将 Host 提交的任务交给 Device？

实际操作：
在 hello world 程序上，**分析真实编译产物**，可以使用工具包括：
- `readelf` 能分析 ELF 结构，但不能保证直接解析内部设备代码；
- 结合 CANN 提供的 `msobjdump` 等工具确认。

区分编译器前端、代码生成、链接器与运行时。不要把这些不同阶段统称为“编译”。最终建立**一张由真实构建日志和二进制检查结果支撑的 Ascend C 编译链路图。**

# 主题二

**相同的源代码为何能以两种完全不同的机制在 WSL 中执行**？

实验基于原始代码，在 WSL 上运行。**验证两种模式的真实差异**。比较：二进制产物、 gdb 调试追踪、引入错误观察。

# 主题三

**Fat Binary（Fatbin，胖二进制）** 是 Ascend C 已有的机制，类似 CUDA。在源码和机器指令之间，还有中间层吗？是什么？

官方承认了 “AscendNPU IR”，[AscendNPU IR](https://gitcode.com/Ascend/AscendNPU-IR/blob/master/docs/source/zh_cn/introduction/introduction.md)，可以再深入探讨。

通过这个项目深入，建立三种能够迁移到其他 AI 计算平台的能力：
- **第一，理解异构程序的构建和执行。**
- **第二，知道如何透过抽象层观察程序。**
- **第三，识别自己的优化控制边界。**
